> 项目：慢病专病全周期一体化健康守护体系

## 一、整体模块架构

将平台分为 **系统管理域** 和 **业务域** 两大块，严格隔离，基础模块不与业务模块混在一起：

```
慢病专病全周期一体化健康守护体系
│
├── 系统管理域（基础支撑，所有业务模块依赖）
│   ├── 用户管理
│   ├── 角色管理
│   ├── 菜单管理
│   ├── 机构管理
│   ├── 数据字典
│   ├── 参数设置
│   ├── 操作日志
│   └── 登录日志
│
├── 业务域
│   ├── 用户档案与画像
│   ├── 数据接入与处理（HIS/LIS 对接）
│   ├── 干预与随访管理
│   ├── 评估、筛查与统计分析
│   └── ……（后续业务模块）
│
└── 公共能力层（横切，被上面两层调用）
    ├── 认证鉴权（JWT + RBAC）
    ├── 文件存储
    ├── 消息通知
    └── 数据权限引擎
```

## 二、系统管理模块 — 功能清单

### 2.1 用户管理

| 功能 | 说明 |
|------|------|
| 用户列表 | 分页表格：用户名、姓名、手机号、所属机构、科室、角色、状态、创建时间 |
| 搜索筛选 | 用户名/姓名模糊搜索、机构筛选、角色筛选、状态筛选 |
| 新增用户 | 用户名（唯一）、姓名、手机号、初始密码、所属机构、科室、角色（多选）、状态 |
| 编辑用户 | 修改基本信息、调整角色、调整机构/科室 |
| 重置密码 | 管理员手动重置为默认密码 |
| 启用/禁用 | 禁用后无法登录 |
| 删除 | 逻辑删除，已关联业务数据的用户建议仅禁用 |
| 数据权限范围 | 分配该用户可见的数据范围（全平台/医共体/本机构/本科室/本人） |

### 2.2 角色管理

| 功能 | 说明 |
|------|------|
| 角色列表 | 角色名称、角色标识(key)、数据范围、排序、状态、创建时间 |
| 新增/编辑 | 角色名、标识、排序、状态、备注 |
| 菜单权限分配 | 树形勾选：目录 → 菜单 → 按钮（三级） |
| 数据权限设置 | 全部数据 / 本机构 / 本科室 / 本人 / 自定义 |
| 关联用户查看 | 查看当前角色下有哪些用户 |
| 预设角色 | 系统内置：超级管理员、机构管理员、科室主任、医生、护士、健康管理师、审核人员 |

### 2.3 菜单管理

| 功能 | 说明 |
|------|------|
| 树形表格 | 菜单名称、图标、路由路径、组件路径、权限标识、排序、类型、状态 |
| 三种类型 | **目录**（分组）、**菜单**（页面）、**按钮**（操作权限点） |
| 新增/编辑 | 上级菜单（树形选择）、类型、名称、图标、路由、组件、权限标识、排序、是否外链、状态 |
| 权限标识规范 | 格式 `模块:资源:操作`，如 `system:user:add`、`followup:task:edit` |
| 状态控制 | 停用后该菜单对所有角色不可见，但不删除配置 |

### 2.4 机构管理

| 功能 | 说明 |
|------|------|
| 机构列表 | 机构名称、机构编码、机构类型、上级机构、联系人、电话、状态 |
| 树形结构 | 医共体牵头院 → 成员单位，支持多级 |
| 科室管理 | 机构下属科室 CRUD，关联医生 |
| 数据隔离基础 | 所有业务数据按机构隔离，机构管理员仅见本机构 |

### 2.5 数据字典

| 功能 | 说明 |
|------|------|
| 字典类型 | 类型名称、类型编码（如 `sys_user_sex`）、状态、备注 |
| 字典值 | 标签、值、排序、状态、样式标记（tag 颜色） |
| 二级管理 | 左侧类型列表 → 右侧该类型下的字典值 |
| 缓存 | 字典数据前端加载后缓存，下拉组件统一调用 |
| 典型数据 | 性别、是否、状态、日志类型、病种分类、随访方式等 |

### 2.6 参数设置

| 功能 | 说明 |
|------|------|
| 系统参数 | 键值对配置，如密码策略、会话超时时间、登录失败锁定次数 |
| 业务参数 | 如默认随访周期、预警阈值默认值等可配置项 |
| 分组管理 | 按模块分组展示，支持搜索 |

### 2.7 操作日志

| 功能 | 说明 |
|------|------|
| 日志列表 | 操作模块、操作类型、操作人、IP、地点、状态、耗时、操作时间 |
| 详情查看 | 请求方法、URL、参数、返回结果、异常信息 |
| 搜索 | 按模块、操作人、时间范围、状态筛选 |
| 自动记录 | 通过 AOP 注解自动采集，无需业务代码侵入 |

### 2.8 登录日志

| 功能 | 说明 |
|------|------|
| 日志列表 | 用户名、IP、登录地点、浏览器、操作系统、状态、提示消息、登录时间 |
| 搜索 | 按用户名、IP、时间范围、状态筛选 |
| 在线用户 | 查看当前在线会话，支持强退 |

## 三、后端技术栈选型

### 3.1 项目特征分析

| 维度 | 判断 |
|------|------|
| 用户规模 | 医疗机构内部使用，管理后台百级用户，移动端千~万级患者 |
| 并发量 | 中等，非电商/社交类高并发场景 |
| 数据一致性 | **高**，医疗数据、随访记录、签约关系要求强一致 |
| 外部集成 | HIS/LIS 系统对接（HL7/FHIR 等医疗协议） |
| 团队规模 | 中小团队（投标项目，通常 3~6 人开发） |
| 运维能力 | 医院信息科或云部署，运维人力有限 |
| 行业生态 | 医疗信息化行业 Java 生态最成熟 |

### 3.2 推荐技术栈

| 层次 | 选型 | 理由 |
|------|------|------|
| 语言 | Java 17+ | 医疗行业主流，人才储备充足，生态完善 |
| 框架 | Spring Boot 3.x | 快速开发，内嵌 Tomcat，开箱即用 |
| ORM | MyBatis-Plus | 国内医疗项目标配，代码生成 + 通用 CRUD |
| 数据库 | MySQL 8.0 | 成熟稳定，医疗行业广泛使用 |
| 缓存 | Redis | 字典缓存、会话管理、验证码、限流 |
| 认证 | Sa-Token 或 Spring Security + JWT | Sa-Token 更轻量，权限模型完善 |
| 接口文档 | Knife4j (Swagger 增强) | 自动生成 API 文档，前后端协作 |
| 日志 | SLF4J + Logback + AOP 注解 | 操作日志自动采集 |
| 文件存储 | MinIO（私有部署）或 阿里云 OSS | 报告、头像等文件存储 |
| 消息队列 | RabbitMQ（按需引入） | 异步通知、短信发送、预警推送 |
| 定时任务 | XXL-JOB 或 Spring 内置 @Scheduled | 随访提醒、预警扫描、数据同步 |

### 3.3 架构判断：模块化单体，预留拆分能力

#### 不建议上微服务的理由

| 因素 | 分析 |
|------|------|
| 团队规模 | 3~6 人团队维护微服务架构成本过高，基础设施（网关、注册中心、配置中心、链路追踪）消耗大量精力 |
| 并发压力 | 管理后台百级用户，不存在高并发拆分需求 |
| 数据一致性 | 医疗数据跨模块关联多（用户→签约→随访→评估），微服务下分布式事务是噩梦 |
| 部署运维 | 医院场景运维能力有限，K8s + 多服务部署维护成本不现实 |
| 开发效率 | 项目初期需求变化快，单体迭代速度远快于微服务 |

#### 采用模块化单体（Modular Monolith）

在代码层面严格分模块、分 Maven Module，保持边界清晰：

```
health-guardian/
├── hg-common/              # 公共工具、异常定义、通用实体
├── hg-framework/           # 框架配置：安全、缓存、日志AOP、全局异常
├── hg-system/              # 系统管理：用户、角色、菜单、字典、日志
├── hg-auth/                # 认证鉴权：登录、token、权限校验
├── hg-org/                 # 机构管理：机构、科室、团队
├── hg-patient/             # 患者档案（后续业务）
├── hg-followup/            # 随访管理（后续业务）
├── hg-integration/         # HIS/LIS 对接（后续业务）
├── hg-admin-api/           # 管理后台 REST 接口聚合层
├── hg-mobile-api/          # 移动端 REST 接口聚合层
└── pom.xml
```

**好处：**
- 各模块代码隔离，编译时能发现跨模块违规依赖
- 未来如果确实需要拆分（比如 HIS 对接模块独立部署），可以直接拆出独立服务
- 当前阶段只部署一个 JAR，运维简单
- 团队按模块分工，职责清晰

#### 未来什么情况下考虑拆分

| 触发条件 | 拆分方向 |
|----------|----------|
| 移动端患者量级到 10 万+，C 端接口压力大 | `hg-mobile-api` 独立部署 |
| HIS/LIS 对接频繁变更，需要独立发版 | `hg-integration` 独立为集成平台 |
| 数据分析/大屏需要独立计算资源 | 拆出数据分析服务 |
| 多地区部署，各地独立数据 | 整体微服务化 + 多租户 |

## 四、数据库设计原则

### 4.1 命名规范

| 规则 | 说明 | 示例 |
|------|------|------|
| 表名 | 小写 + 模块前缀 + 下划线分隔 | `sys_user`、`sys_role`、`biz_followup_record` |
| 字段名 | 小写 + 下划线分隔 | `user_name`、`create_time` |
| 主键 | 统一命名 `id`，类型 `BIGINT` | 雪花算法或数据库自增 |
| 外键关联字段 | `{关联表}_id` | `role_id`、`org_id`、`dept_id` |
| 索引 | `idx_{表名简写}_{字段}` | `idx_user_org_id` |
| 唯一索引 | `uk_{表名简写}_{字段}` | `uk_user_username` |

### 4.2 公共字段（所有业务表必须包含）

```sql
-- 每张表统一携带以下字段，由框架自动填充
id           BIGINT       NOT NULL COMMENT '主键',
create_by    VARCHAR(64)  DEFAULT NULL COMMENT '创建人',
create_time  DATETIME     DEFAULT NULL COMMENT '创建时间',
update_by    VARCHAR(64)  DEFAULT NULL COMMENT '更新人',
update_time  DATETIME     DEFAULT NULL COMMENT '更新时间',
deleted      TINYINT(1)   DEFAULT 0 COMMENT '逻辑删除（0正常 1删除）',
remark       VARCHAR(500) DEFAULT NULL COMMENT '备注'
```

### 4.3 数据隔离字段

```sql
-- 所有业务数据表必须携带机构归属字段，用于数据权限过滤
org_id       BIGINT       NOT NULL COMMENT '所属机构ID'
```

查询时由框架拦截器自动追加 `org_id` 条件，业务代码无需手动处理。

### 4.4 设计原则

| 原则 | 说明 |
|------|------|
| 逻辑删除 | 所有表使用 `deleted` 字段软删除，不做物理删除，医疗数据可追溯 |
| 字典驱动 | 状态、类型、分类等可枚举字段统一用 `TINYINT` 存储编码，含义由数据字典表维护，代码中不硬编码中文 |
| 不使用外键约束 | 表之间通过 ID 关联，不在数据库层建外键约束（避免级联问题，便于拆分），关联完整性由应用层保证 |
| 金额/精度 | 涉及金额用 `DECIMAL(12,2)`，涉及检验值用 `DECIMAL(10,2)`，不用 `FLOAT/DOUBLE` |
| 时间统一 | 全部使用 `DATETIME`，不用 `TIMESTAMP`（避免 2038 问题），时区由应用层处理 |
| 大字段分离 | 长文本（如评估报告内容）用 `TEXT`，与主表分离或延迟加载，避免影响列表查询性能 |
| 索引策略 | 高频查询字段建索引；组合查询建联合索引，遵循最左前缀原则；单表索引不超过 5 个 |
| 敏感数据 | 身份证号、手机号等加密存储（AES），查询时解密；日志中脱敏输出 |
| 枚举扩展 | 预留扩展位，如状态字段用 `TINYINT` 而非 `ENUM` 类型，方便新增状态值 |
| 变更可追溯 | 关键业务表（用户档案、签约、随访记录）配套设计 `_history` 或 `_log` 表记录变更 |

### 4.5 系统管理模块核心表结构概览

```
sys_user          用户表
sys_role          角色表
sys_menu          菜单表
sys_user_role     用户-角色关联表
sys_role_menu     角色-菜单关联表
sys_org           机构表
sys_dept          科室表
sys_dict_type     字典类型表
sys_dict_data     字典数据表
sys_config        参数配置表
sys_oper_log      操作日志表
sys_login_log     登录日志表
```

### 4.6 数据量预估与分区策略

| 表 | 预估量级 | 策略 |
|----|----------|------|
| `sys_user` | 百~千级 | 无需特殊处理 |
| `sys_oper_log` | 百万级/年 | 按季度分区或定期归档清理 |
| `sys_login_log` | 十万级/年 | 按年归档 |
| 业务表（随访/档案） | 十万~百万级 | 初期单表，后期按 `org_id` 或时间分表 |

## 五、前端技术栈与低分辨率适配

### 5.1 技术栈

| 端 | 选型 | 说明 |
|----|------|------|
| 管理后台 | Vue 3 + Element Plus | 已有基础，HIS 风格 |
| 移动端 | uni-app + 微信小程序 | 已有基础 |
| 状态管理 | Pinia | 轻量，适合中等规模 |
| HTTP | Axios | 已有封装 |

### 5.2 低分辨率适配背景

医院场景常见显示器分辨率：

| 分辨率 | 占比趋势 | 说明 |
|--------|----------|------|
| 1920×1080 | 主流 | 新采购设备 |
| 1680×1050 | 仍有存量 | 5年前设备 |
| **1366×768** | **重点关注** | 基层卫生院/老旧设备大量存在 |
| 1440×900 | 少量 | MacBook 旧款 |
| 1024×768 | 极少但存在 | 非常老旧设备，可考虑最低兼容 |

### 5.3 设计基准调整

| 项目 | 原方案 | 调整后 |
|------|--------|--------|
| 设计基准宽度 | 1440px | **1366px**（覆盖主流低端） |
| 最小兼容宽度 | 无 | **1280px**（低于此宽度提示升级设备） |
| 侧边栏宽度 | 216px 固定 | **可折叠，展开 216px / 收起 64px** |
| 顶栏高度 | 56px | 保持，但低分辨率下可缩至 **48px** |

### 5.4 具体适配策略

#### 侧边栏

- 展开态（≥1440px 默认）：216px，显示完整菜单文字
- 收起态（<1440px 或手动折叠）：64px，仅显示图标
- 悬浮展开：鼠标 hover 收起态侧边栏时浮层展示子菜单

#### 表格

| 策略 | 说明 |
|------|------|
| 列可配置 | 用户可自行选择显示/隐藏列，低分辨率下隐藏非关键列 |
| 横向滚动 | 表格内容区允许横向滚动，固定左侧操作列和右侧操作列 |
| 紧凑模式 | 提供「紧凑/舒适」行高切换，默认紧凑（行高 36px） |
| 分页默认 20 条 | 保持，但提供 10/20/50 切换 |
| 筛选区可折叠 | 搜索条件超过 3 个时默认折叠，展开后不遮挡表格 |

#### 弹窗/抽屉

| 策略 | 说明 |
|------|------|
| 弹窗最大宽度 | `min(900px, 90vw)`，避免低分辨率下溢出 |
| 表单布局 | 低分辨率下表单改为**单列**布局，宽屏下双列 |
| 抽屉宽度 | `min(600px, 70vw)` |

#### CSS 响应式断点

```css
/* 全局响应式断点 */
:root {
  --sidebar-width: 216px;
  --topbar-height: 56px;
}

/* 中等屏幕：侧边栏自动收起 */
@media (max-width: 1440px) {
  :root {
    --sidebar-width: 64px;
  }
}

/* 小屏幕：进一步压缩 */
@media (max-width: 1366px) {
  :root {
    --topbar-height: 48px;
  }
  .table-row { height: 36px; }
  .form-layout { grid-template-columns: 1fr; }
}

/* 最小宽度保护 */
@media (max-width: 1280px) {
  .min-width-warning { display: block; }
}
```

#### 最低宽度提示

当检测到视口宽度 < 1280px 时，顶部显示一条提示：

> ⚠ 当前屏幕分辨率较低，建议使用 1366×768 及以上分辨率以获得最佳体验。

用户可关闭，下次登录不再提示（localStorage 记录）。

### 5.5 更新到 UI 设计规范

| 项目 | 规范值 |
|------|--------|
| 设计基准 | 1366px 宽（非 1440px） |
| 最小兼容 | 1280px |
| 侧边栏 | 可折叠 216px / 64px |
| 表格行高 | 默认 36px（紧凑），可切 44px（舒适） |
| 表单布局 | ≤1366px 单列，>1366px 双列 |
| 弹窗宽度 | `min(900px, 90vw)` |
| 顶栏高度 | 默认 56px，≤1366px 时 48px |

```
│           └── login.vue    # 登录日志页
├── store/
```

## 七、开发顺序建议

```
第1步：菜单管理 → 改造侧边栏为动态渲染（其他模块的页面路由依赖它）
第2步：角色管理 → 先建角色，用户才能关联
第3步：用户管理 → 关联角色，完成基本 RBAC 闭环
第4步：机构管理 → 为业务数据提供组织归属
第5步：数据字典 → 为后续业务模块提供下拉数据源
第6步：参数设置 → 可配置项集中管理
第7步：日志管理 → 纯展示页面，独立性强，最后做
```

## 八、总结

```
系统管理域（8 个功能模块，独立于业务）
├── 用户、角色、菜单、机构、字典、参数、操作日志、登录日志

后端技术栈
├── Java 17 + Spring Boot 3 + MyBatis-Plus + MySQL + Redis

├── 命名规范 + 公共字段 + 逻辑删除 + 字典驱动
├── 数据隔离（org_id）+ 敏感数据加密 + 变更可追溯

前端适配
├── 设计基准 1366px，最小兼容 1280px
├── 侧边栏可折叠 + 表格紧凑 + 表单响应式 + 弹窗自适应

前端技术栈
├── 管理后台：Vue 3 + Element Plus
└── 移动端：uni-app 微信小程序
```
